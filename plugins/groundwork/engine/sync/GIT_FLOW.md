# git_flow.py: the settings.git block

`sync\git_flow.py` reads an optional `settings.git` block from `siteoffice.json` (schema v2)
through the same manifest parent-walk as `owners`: the root manifest's block is inherited and the
node's own keys win. An invalid value falls back to its default and adds an amber note to the
step's preview; it never crashes a step.

| Key | Default | Meaning |
|---|---|---|
| `profile` | `"code"` | Only `"code"` is honoured in this cut. |
| `main` | `"main"` | Branch that `start` pulls and branches from. |
| `protected` | `["main", "master"]` | Branches `save` refuses to commit on. `main` is always included, even when this list is empty or omits it; on Windows the comparison ignores case. |
| `checks` | `[]` | Ordered command strings run by `check` (`shell=True`, the repo's own commands). |
| `checkTimeoutSeconds` | `600` | Per-command timeout for `check`. A timeout is `blocked`. |
| `denylist` | `".git-denylist"` | Path relative to the repo root: one glob per line, `#` comments. A missing file means empty. |
| `pr.approvals` | `0` | Whole number. `land` refuses a pull request with fewer approvals, counting the latest review of each author. 0 means a solo landing needs none. |

Denylist semantics: one glob per line, `#` starts a comment, blank lines are skipped. A glob
without a slash also matches the bare file name anywhere; `dir/` means everything under `dir`;
a leading `./` is ignored; matching ignores case. There is no negation and no `**` handling. A
missing file means empty. An unreadable file (a directory, bad encoding, no permission) is an
error that refuses the save, and the message names the file, never its content. A UTF-8 BOM
and CRLF line ends are accepted.

Steps: `python sync\git_flow.py start <slug> | save [--type T --scope S --subject TEXT] | check | propose [--title TEXT] | land [--subject TEXT] | abort`,
each with `--apply` (default is a preview that changes nothing), `--repo <dir>`, `--harness`,
`--model`. Exit code 0 is `pass`, 2 is `refused`, 3 is `blocked`.
A command line mistake also exits 2; it prints a line starting `usage error:` to stderr and nothing to stdout.
The directory must be the git root (a nested manifest node is refused, exit 2, nothing written): run from the git root or pass `--repo <git root>`.
Receipts: one line per applied step in `_log\runs\git-flow.ndjson` (gitignored).
Sync receipts: `git_ops` writes `_log\sync-receipt-<timestamp>.json` after each commit. A `save` that has other work also commits the pending ones, which belong to earlier commits; the receipt of the commit being made is written after it and rides along with the next save. Receipts alone are never a save (still "Nothing to save"), the commit message and its inferred type and scope describe only the work, and a receipt that matches the denylist is skipped.
Secrets scan limit: conversion on new (untracked) files is not scanned: clean filters, and working-tree-encoding (for example IBM037) declared in a committed .gitattributes. A tracked file is scanned through the diff.
Policy files: `save` refuses the whole save (exit 2, nothing staged) when git's changed paths hold a policy file: any `siteoffice.json` at any depth, the configured `denylist` file, or any `.gitignore`. Names are compared without regard to case; paths under `_log/` are ignored. A policy change needs a deliberate commit by a human, not an agent save.
Renames: a rename is listed as a deletion of the old path plus an addition of the new path, and each is vetted (owner check, denylist, secrets scan) on its own.
Commit message: the subject and the scope are scanned with the same secret rules as file content; a hit refuses naming the field and the rule, never the matched text.
Protected branches: main and master are always protected, in addition to `protected` and `main`. No manifest, its own or one inherited from a parent, can remove them.
Denylist: the union of `.git-denylist` (repo root) and the configured `denylist` path. A missing file is empty; an unreadable one refuses the save. Both paths are policy files.
Quoted assignments: a name holding key, secret, token or password with a quoted value of 12+ characters is refused, also with a type annotation (`TOKEN: str = "..."`), a string prefix (b, f, r, u, rb, br, fr, rf, any case), a walrus (`:=`) or triple quotes (the value starts on the same line as the opener). Backtick strings are not covered.
File names: every file name to be committed is scanned, not only the ones the commit body lists (it lists at most 20). The scan uses the same rules as file content and covers both sides of a rename and a deletion. A secret-shaped file name or directory name refuses the save before anything is staged (the refusal names the field "a file name" and the rule, never the name); rename the file. The commit body is scanned too, as a second guard.
Checks come only from manifests inside the repo: `settings.git.checks` run through a shell, so a `checks` list inherited from a siteoffice.json above the repo is ignored and an amber note says so (the commands are not printed). Every other inherited key still applies.
Quoted assignments, wider forms: a type annotation with spaces, pipes, commas, quotes, brackets or parentheses (`api_key: str | None = "..."`, `password: Dict[str, str] = "..."`, `secret: Annotated[str, Doc("x")] = "..."`, TypeScript `password?: string = "..."`) and a subscript target with a secret name in its quoted key (`os.environ["API_KEY"] = "..."`, `config['password'] = '...'`) are refused like a plain assignment.
Word boundaries: only `sk-` keeps a word boundary. `gh[pousr]_` (36+ characters after the prefix) and `xox[baprs]-` (10+ after the prefix) are found even when glued to a name (`TOKEN_ghp_...`, `KEY_xoxb-...`), in content, in file names and in redaction; ordinary names such as `task-list-...` and `risk-assessment-...` still pass.
Annotation parentheses: the annotation may hold `(` and `)` but never `=` or `:`, so `Annotated[str, Field(min_length=1)]` is not covered; it stays one bounded run of at most 200 characters.
Untracked symlinks: the link text (its target path) is scanned as an added line, besides the content of the target; a key-shaped target path refuses the save naming the path and the rule, never the text. A tracked symlink that is retargeted is scanned through the diff.
start: a pull state of `error` or `conflict`, or a failed pull, refuses before any branch is made; the message gives the state or reason, never file content. When another worktree has `main` checked out (the deploy checkout), `start` does not check `main` out: it fetches origin and creates the branch from `origin/<main>` with no upstream, the preview names the worktree, and a failed fetch refuses before any branch is made.
propose: pushes the work branch (`git push -u origin <branch>`) and opens a pull request with `gh pr create --base <main> --head <branch>`. It refuses on a detached, unknown or protected HEAD, off a `work/<owner>/<slug>` branch, with a dirty tree (paths under `_log/` are ignored), with no commit on top of `origin/<main>`, and without a passing `check` receipt for the current HEAD ("Run check on this commit first."; the newest `check` receipt for that commit decides). A check that passed with 0 checks configured counts as green and the body says "No checks ran". The title is the newest commit subject unless `--title TEXT` is given; the body lists the commit subjects and the receipts since `start` (step, outcome, each check with exit and seconds). A given title is refused (exit 2, nothing pushed) when it is empty once stripped, longer than 240 characters (`PR_TITLE_LIMIT`, never cut short) or more than one line; the preview shows the title that would be used. Title and body go through the secret rules; a hit refuses naming the field and the rule, never the text. When an open pull request for the branch exists, propose pushes the new commits to it and creates nothing; a given `--title` does not edit that pull request, and the output says the existing title was not changed. More than one open pull request for the branch is refused.
land: merges the open pull request of the current work branch with a merge commit (`gh pr merge <n> --merge --match-head-commit <sha>`, never squash or rebase; `--subject TEXT` adds `--subject TEXT` for the merge commit subject, otherwise gh's default stands and the call is unchanged). A given subject is checked before gh is called: empty once stripped, longer than 100 characters (`MERGE_SUBJECT_LIMIT`) or more than one line is refused (exit 2, nothing merged), and the secret rules apply (the refusal names the rule, never the text); the preview shows it. It refuses off a work branch, with a dirty tree, with no open pull request, when the pull request head differs from local HEAD ("Push first: run propose."), when `reviewDecision` is `CHANGES_REQUESTED`, with fewer approvals than `pr.approvals`, and when `git merge-tree --write-tree origin/<main> HEAD` reports conflicts (the paths are named). If the branch already contains `origin/<main>`, the passing `check` receipt for HEAD is reused; otherwise the checks run on the merge result, in a detached temporary worktree of a merge commit that is always removed. A red or timed-out check is `blocked`. After the merge it checks out `<main>`, fast-forwards it to `origin/<main>` (`git merge --ff-only`, not `git_ops.pull`, which would add a local merge commit), deletes the local branch (`git branch -d`) and the remote branch (`git push origin --delete`; a branch GitHub already deleted is fine). If the merge happened but a cleanup step failed, the outcome is `pass` with an amber note naming what remains; the merge is never reported as failed.
abort: on a `work/<owner>/<slug>` branch only. Stashes uncommitted changes first when there are any (`git stash push --include-untracked -m parked/<owner>/<slug>`), renames the branch to `parked/<owner>/<slug>` and checks out `<main>`. Never deletes a branch, a commit or a file, and never touches the remote branch.
gh: located with `shutil.which` and called through the module-level `GH_COMMAND` list (tests point it at `sync\tests\gh_stub.py`). A missing gh is `blocked` with "Install GitHub CLI: winget install --id GitHub.cli, then run gh auth login."; a failing `gh auth status` is `blocked` with "Run gh auth login.". No token is read, passed or stored here. gh output is redacted before it reaches a preview, a refusal or a receipt.
Receipts: `propose` and `land` add one optional key, `pr`, to the sixteen keys: `{"number": 7, "url": "...", "merge_commit": "..."}` (`merge_commit` is empty on `propose`). A refused or blocked step before the pull request exists has no `pr` key. Receipts record no step arguments, so `--title` and `--subject` leave no trace in them (the keys stay as listed).
Limits: unresolved review threads are not checked (they need a GraphQL call); `land` refuses on `CHANGES_REQUESTED` instead. The temporary worktree holds tracked files only, so a check that needs an untracked or ignored file fails there. A `land` preview runs `git fetch origin` (it moves only the remote-tracking refs).
